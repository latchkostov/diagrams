# C4 views: one architecture model, several levels of detail

Status: research and proposed design, checked **2026-10-14**. The owner approved this docs-only research on
2026-10-14: “the C4 style multi-view would be something really cool”. Branch `research/c4-views`, fresh from
`origin/master` at `be7b194`. Implementation follows the scheduled CanvasView/Inspector refactoring round;
this document neither adds application behaviour nor expands approval for other simulation work.

## Recommendation

Keep one model of people, software systems, containers, components and relationships. A view selects a scope,
projects its relationships and stores its own layout. Renaming Orders API changes every view; moving its card
changes only the current view. Existing files remain single-level diagrams with exactly their current editing
and playback. Creating inner detail is optional, and double-click continues to open Properties.

Run one simulation over the most detailed **executable** model. Context and Container views summarize that run;
they never create another engine, another worker fleet or synthetic flows. Start with Context, Container and
Component views; support a Landscape projection using the same machinery. Keep Code links and true deployment
instances as later work. Four implementation PRs are proposed in §6, with a useful read-only first release.

This builds on [diagram semantics](diagram-semantics.md), [planning](planning-model.md),
[routing and endpoints](routing.md), [autoscaling](autoscaling.md), [simulation semantics](../SIMULATION.md),
[UX principles](../UX-PRINCIPLES.md) and [quality gates](../QUALITY.md). Current code, especially
[`src/model/types.ts`](../../src/model/types.ts), is authoritative where older research describes something
already superseded. P1/P2 and `diagrams/v2` exist here; routing, autoscaling and other proposed revisions must
be composed with their eventual merged contracts, not assumed implemented.

## 1. Research: what to adopt

Primary sources were checked on the date above. The tool descriptions below are documented capabilities;
the recommendations and comparisons are design judgements, not hands-on account evaluations.

### The C4 model

C4 is a hierarchy of abstractions with four static diagram levels, rather than a required visual theme.
Teams need only the levels useful to their audience; Context and Container often suffice.
[C4 diagram overview](https://c4model.com/diagrams).

| View       | Scope and audience                                                                                                                                                    | Live Diagrams interpretation                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Context    | One software system, the people using it and connected systems; understandable without implementation detail. [Context](https://c4model.com/diagrams/system-context). | System cards, purposeful relationship labels, optional summarized live activity.                                                                |
| Container  | Applications and data stores inside one system, with connected people/systems and technology choices. [Container diagram](https://c4model.com/diagrams/container).    | Services, functions, databases and individual queues/topics are typical executable leaves.                                                      |
| Component  | Functional building blocks inside one container, plus connected containers, people and systems. [Component diagram](https://c4model.com/diagrams/component).          | Optional internal design; components share their container's runtime resources when execution is enabled.                                       |
| Code       | Implementation of one component: classes, interfaces, functions or tables, often generated by development tools. [Code](https://c4model.com/diagrams/code).           | Defer a code graph/editor; initially link documentation from a component's Properties. No fourth empty canvas.                                  |
| Landscape  | People and systems across an organization, with no single focal system. [Landscape](https://c4model.com/diagrams/system-landscape).                                   | Root projection over selected systems; same level of abstraction as Context, different scope.                                                   |
| Dynamic    | Ordered interactions for a feature or use case, using elements of the static model. [Dynamic](https://c4model.com/diagrams/dynamic).                                  | Project existing traces, sequence diagrams and narrated simulations onto a chosen level. An authored story is distinct from observed execution. |
| Deployment | Instances of systems/containers on nested infrastructure in an environment, with supporting infrastructure. [Deployment](https://c4model.com/diagrams/deployment).    | Preserve today's infrastructure diagrams; true instance-to-container/environment mapping needs a separate later contract.                       |

A C4 container is an application or data store, independent of Docker or physical hosting. A component groups
functionality behind an interface and is not separately deployable; components in one container share its
process. These distinctions prevent a Kubernetes namespace becoming a software system or every class gaining
replicas. [Container abstraction](https://c4model.com/abstractions/container),
[Component abstraction](https://c4model.com/abstractions/component).

C4 specifically recommends individual queues/topics as containers, or implicit “via” interactions, rather
than treating the whole message bus as one application hop. Keep queues/topics explicit in the executable
model: hiding them in a view must preserve their buffering, groups and backpressure. A Kafka cluster drawing
remains infrastructure. [Queues and topics](https://c4model.com/abstractions/queues-and-topics).

### Structurizr: model and views

Structurizr's DSL defines a workspace with separate `model` and `views` sections. Stable identifiers connect
people, software systems, nested containers/components and relationships to scoped views, whose inclusion
and layout are independent. This is the closest reference for the file contract.
[DSL example](https://docs.structurizr.com/dsl/example),
[Language reference](https://docs.structurizr.com/dsl/language).

Its implied relationships roll a lower-level relationship up to ancestors. The documented default avoids
creating multiple implied relationships between the same pair, so the first relationship can determine the
summary. Adopt roll-up, but retain **all contributor IDs** and keep Message, Request and different dependencies
separate. Never let input order erase a second route or a secret dependency.
[Implied relationships](https://docs.structurizr.com/dsl/cookbook/implied-relationships/).

### IcePanel: reusable objects and discoverable navigation

IcePanel models reusable objects across three connected C4 levels, linking to implementation instead of
drawing Level 4. Editing an object's name updates its appearances. Its top navigation shows hierarchy and
diagrams; a magnifier and nested-object count open lower detail. Adopt persistent identity, a compact
navigation surface and a visible inner-detail cue. Avoid automatically creating an empty diagram when
someone merely tries to navigate. [Diagramming](https://docs.icepanel.io/core-features/diagramming).

IcePanel flows tell a use case step by step over existing objects/connections, including detail across
levels. They are a useful reference for presenting stories, not evidence that IcePanel simulates queue
capacity or controller decisions. Live Diagrams should reuse its executable simulations and trace lineage
instead of introducing a second flow authoring engine. [Flows](https://docs.icepanel.io/visual-storytelling/flows),
[Getting started](https://docs.icepanel.io/getting-started).

### Ilograph: perspectives and contexts are different axes

Ilograph perspectives show different relations over reusable resources. Contexts change their surrounding
resource hierarchy without changing those relations. This suggests separating **what belongs to an
application** from **how we group it for this story**. Adopt view filters and visual boundaries as presentation
choices; defer alternative semantic parent trees and a permanent perspectives/contexts panel.
[Perspectives](https://www.ilograph.com/docs/editing/perspectives/),
[Contexts](https://www.ilograph.com/docs/editing/contexts/).

### Lucid and Miro: useful templates, insufficient identity guarantees

Lucid's C4 template provides a customizable example and shapes/connectors. Its guide explains drill-down
using layers and constructing the next level separately; its Mermaid option produces a static visual.
[Lucid template](https://lucid.co/templates/c4-model-example),
[Lucid C4 guide](https://lucid.co/blog/c4-model).

Miro's C4 Architecture template offers a board starting point for explaining architecture.
[Miro template](https://miro.com/templates/c4-architecture/).

**Inference from those template workflows:** neither template establishes canonical object IDs, valid parent
references or relationship provenance across levels. Copying a service into another layer/frame can leave
names and arrows inconsistent; linked navigation alone does not fix that. This critique concerns templates,
not a claim that the entire products lack integrations, data linking or other modelling features. Keep their
ease of starting from an example, while making a second view reuse the model rather than copy shapes.

### Mermaid C4: an exchange target, not the storage model

Mermaid documents `C4Context`, `C4Container`, `C4Component`, `C4Dynamic` and `C4Deployment`, with
`Person`, `System`, `Container`, `Component`, boundary blocks and `Rel` statements. C4 syntax remains
experimental; layout is influenced by declaration order and layout configuration. It does not promise
Live Diagrams' coordinates, view navigation, executable semantics or a complete legend/tag/link feature set.
Export a documented subset per view, with loss reporting and pinned fixture syntax. Keep native JSON
authoritative. [Mermaid C4 syntax](https://mermaid.js.org/syntax/c4).

## 2. Model and file format

### Canonical identity and optional hierarchy

Today `DiagramFile` owns nodes, edges, `groups` (UI: boundaries), annotations, layer order and saved
simulations. Nodes have absolute `x/y`, optional `group`, stencil and props; edges have stable endpoints,
relationship semantics and attachment sides. Boundaries have rectangles, not semantic parents. Shape
annotations may be edge endpoints for documentation and never carry traffic.

Use a normalized architecture document internally, with one canonical record per element and relationship,
and layouts keyed by view ID. Keep C4 kind separate from stencil/`simRole`: PostgreSQL can render as a
container with a store runtime; a system is an aggregate, not a new processor role. An external system can
be an opaque executable API if explicitly configured. A Person is an actor, with optional authored source
behaviour; it is not automatically an HTTP client or a rate generator.

Hierarchy constraints: Person and Software system are roots; Container has one Software system parent;
Component has one Container parent. No cycles, duplicate IDs or multiple semantic parents. An unclassified
`node` kind preserves flat diagrams and infrastructure without guessing a C4 category. It is a root and
appears in flat/custom views until explicitly classified. Partial adoption is valid: do not silently hide
unclassified nodes; a C4 view reports how many are outside its scope and offers the original view.

The same element can appear in many views of the same document. Reuse means the **same ID**, not a clone with
the same label. Separate replicas, regions and deployment instances are not extra C4 parents. Ownership and
deployment must remain distinct when the instance model is eventually added.

### Proposed TypeScript contract

Design sketch only. These types reuse current contracts; no schema/type changes are made on this branch.
Structural format version and the existing planning revision are independent compatibility checks.

```ts
import type {
  DiagramFile,
  DiagramNode,
  DiagramEdge,
  DiagramGroup,
  DiagramAnnotation,
  EdgeRelation,
  Side,
} from "../../src/model/types";

type ElementKind = "node" | "person" | "softwareSystem" | "container" | "component";
type RuntimeNode = Pick<DiagramNode, "stencil" | "props">;

interface ArchitectureElement {
  id: string;
  kind: ElementKind;
  parent?: string; // semantic ownership, never a visual boundary ID
  label: string;
  sublabel?: string;
  description?: string;
  technology?: string;
  external?: boolean;
  stencil?: string; // visual choice; runtime resolution uses this same stencil
  execution?: { mode: "atomic"; props?: RuntimeNode["props"] } | { mode: "detail"; props?: RuntimeNode["props"] };
  // Absent execution = documentation only. Detail requires the §4 compiler.
}

interface ArchitectureRelationship extends Omit<DiagramEdge, "sourceSide" | "targetSide"> {
  technology?: string;
  execution: "flow" | "documentation";
  realizes?: string[]; // documentation summary's lower-level relationship IDs
  // A non-flow EdgeRelation must always be documentation in the current engine.
}

type ViewScope =
  | { kind: "flat"; elements: string[] }
  | { kind: "landscape"; systems: string[] }
  | { kind: "context"; system: string }
  | { kind: "container"; system: string }
  | { kind: "component"; container: string };

interface ElementPlacement {
  x: number; // absolute view coordinates, never relative to semantic parent
  y: number;
  boundary?: string;
}
interface RelationshipPlacement {
  sourceSide?: Side;
  targetSide?: Side;
}
interface ArchitectureView {
  id: string;
  title: string;
  scope: ViewScope;
  exclude?: string[]; // hides appearances, never deletes model records
  relations?: EdgeRelation[]; // omitted = all, [] = none
  direction?: "LR" | "TB";
  layout: {
    elements: Record<string, ElementPlacement>;
    relationships?: Record<string, RelationshipPlacement>; // projected keys
    boundaries?: DiagramGroup[]; // preserves today's visual boundary fields
    annotations?: DiagramAnnotation[]; // view-owned; shape IDs globally unique
    annotationEdges?: DiagramEdge[]; // documentation only, never rolled up
    layerOrder?: string[];
  };
}
interface ArchitectureFile extends Omit<
  DiagramFile,
  "format" | "nodes" | "edges" | "groups" | "annotations" | "layerOrder" | "direction"
> {
  format: "diagrams/v3";
  elements: ArchitectureElement[];
  relationships: ArchitectureRelationship[];
  views: ArchitectureView[];
  defaultView: string;
}
```

The single `stencil` field serves rendering and runtime profile lookup; omitted stencil on documentation
elements uses a generic C4 visual. Atomic execution requires a valid stencil (unknown IDs keep the existing
generic fallback semantics). A structural Software system has no execution configuration: its executable
containers participate directly. An opaque system can be atomic only without active executable descendants.
`detail` is valid only on a Container and activates explicitly executable components with **one parent-owned
pool**. Its props configure that pool. Systems have no independent replica pool. Components may be atomic or
documentation-only, never detail. `node`/Person can be atomic or documentation-only; a Person never has children. Atomic parents can
have documentation children, but no active executable descendants. Validate these invariants centrally.

V1/V2 support only atomic leaves and non-executing structural parents; component execution/detail pools land
in V3 (§6). In this paragraph V1–V4 name implementation phases, not file-format versions. Unsupported execution
modes must be refused, not loaded as independently provisioned processors. Detail execution needs a new
recognized planning revision composing the merged P3/routing/autoscaling contracts where applicable.

View membership comes from scope plus connected neighbours, not saved copies of nodes. Context maps to root
systems/people; Container shows direct containers in its system and connected external people/systems;
Component shows direct components plus connected sibling containers and external people/systems. Unrelated
neighbours are omitted. A flat view has explicit elements and preserves its existing exact membership.
Default scoped views include new children automatically; exclusions remain explicit. Store an initial layout
for each newly visible element in the same edit that creates it; otherwise use deterministic fallback layout.
Orphan placements from removed elements are pruned atomically.

### Relationship projection and provenance

Flat views bypass roll-up and bundling: retain each original node/edge appearance, including parallel edges,
original edge IDs and attachment sides. Scoped C4 views use the projection below; their derived keys never
replace canonical IDs in saved simulation, check or routing references.

For a view, compile `representative(elementId)`: the visible element itself or its nearest visible ancestor.
Outside the selected system/container, use the scope's neighbour rule above. Resolve both ends of every
relationship through that map. If both resolve to the same aggregate, suppress the self-edge; keep its
contribution in that aggregate's details. If an endpoint has no representative, omit the arrow and report
hidden connected detail in Properties. Never invent a shortcut through an omitted queue or network device.

Group projected arrows by ordered endpoints, resolved relation, and flow kind. Keep ordinary and dead-letter
flow roles distinct. Parallel contributors with different endpoints/routes/groups remain separate canonical
records; a compact arrow lists “3 connections” on inspection. Use a deterministic key from the projection
endpoints/semantic group, not input order or contributor array indices, so reordering records preserves layout.
The derived result contains `relationshipIds`, original endpoints and hidden internal relationships. It is
cached, never saved as another canonical relationship.

Example: `validate(component of Orders API) → charge(component of Payments API)`, with both containers in
Commerce, projects to `Orders API → Payments API` in Commerce's Container view. It is internal to Commerce
and disappears in Context. If Payments API belongs to a separate Payments system, Commerce's Container view
instead shows `Orders API → Payments`, and Context shows `Commerce → Payments`. A second Secret relationship
projects separately; it cannot become a Request. Two components of Orders API talking to each other disappear
into Orders API at Container level, without adding traffic to its external rate.

An authored system-level relationship is documentation until bound to executable leaf connections. Preserve
it as a canonical summary with the proposed `realizes` list of lower relationship IDs. Validate direction,
relation compatibility and descendant endpoints; prohibit cyclic realization. A summary with contributors presents them instead of
adding a second arrow/count. Unbound summaries say “Not simulated”. Changing the summary label changes
its description, never rewrites filters/routes on all its children. Exporters retain the distinction.

### Existing boundaries and annotations

`node.group` migrates to the original view's placement `boundary`; `groups` migrate intact into that view.
Boundary resize, drag, fit and centre-based membership continue as documented. Those gestures change visual
membership, **never `element.parent`**. The same API can be within a Kubernetes boundary in an infrastructure
view and a team boundary in a custom flat view. Neither makes Kubernetes or the team its C4 owner.

Draw the focused C4 parent as a scope frame with its own label, visually distinct from an editable Boundary;
its children are chosen by parent references, not card position. Moving the frame moves appearances only.
Do not allow a frame resize to reparent nodes. A new scope frame uses a different test ID and accessible name.
Use the established solid Boundary and dashed Zone appearances; do not overload Zone as a semantic parent.

Annotations, layer order and shape-ended documentation edges stay view-owned. Do not duplicate notes at every
level or roll a shape endpoint into a software-system relationship. Removing a view previews removal of its
annotations; removing an appearance preserves its element in other views. IDs for elements, relationships,
boundaries, annotations and views are globally unique within v3 to make agent references unambiguous.

### Migration and compatibility

1. On opening v1/v2, adapt in memory to `kind: "node"` elements and one flat view, retaining every ID, stencil,
   prop, edge relation/origin/kind, attachment side, boundary rectangle, annotation, direction and layer order.
   Execution is atomic under the **original planning revision or legacy resolver**, including omitted defaults.
   Shape-ended edges go to that view's annotation edges; ordinary dependencies remain canonical documentation.
   Saved traffic/setup/timeline/expectation references retain IDs. No classification or planning upgrade occurs.
2. Keep the existing v1/v2 writer for a document that still has only flat-compatible content. The original
   file opens, saves and simulates exactly as today; migration is an internal adapter, not a forced upgrade.
   Creating a second view or semantic nesting explicitly opts into v3 in one undo step with a compatibility
   notice. V3 can represent a migrated single-level model too.
3. V3 changes structure: `elements`/`relationships` and `views` replace global geometry collections. Keep title,
   description, colour, privacy, checks and simulations; retain absent planning for migrated legacy playback.
   The v3 reader checks both format and supported planning semantics. Current `native.ts` rejects unknown
   formats, so old clients must refuse v3 rather than display an empty graph or run a different simulation.
4. Update native schema/parser/serializer, storage, clipboard, shared-file decoding, agent validation, simulation
   references and all viewer readers together. Preserve unknown safe extension fields through adapter/writer
   round-trips as well as props, using the existing native preservation rules;
   unsupported required structural/execution semantics fail with an actionable version error. No unknown
   field can bypass reference, collection or input-depth limits.
5. Offer “Export current view as legacy diagram” only as an explicit flattened, lossy drawing. Report lost
   nesting, other layouts, roll-up provenance and execution settings; exclude simulations unless the exact
   flat executable graph and original semantics can be preserved. Numeric pinning cannot make an aggregate
   graph execute equivalently. Native v3 is the full-fidelity export; Undo restores its preceding version.

Proposed browser safety bounds: existing native byte/node/edge/text budgets still apply across the **whole
document**, plus at most 64 views, C4 depth 3 (root system → container → component), 200-character IDs and
bounded total placements (proposed 50,000), annotations and realization references. Flat imports may contain
more nodes than the interactive planner's budget; report unavailable analysis rather than truncating a model.
Index parents/IDs and validate iteratively. Projection costs O(N + E + placements) per changed view/configuration,
with depth bounded; never compare every pair of elements or rebuild indexes on every frame. Treat the new
numeric limits as product proposals, not C4/tool restrictions, and settle them against existing import budgets
in V1. Keep only the active and bounded recent projections cached.

## 3. UX: detail one step away

### Navigation and the double-click conflict

**Explicit conflict:** common drill-down designs use double-click to open a system/container. The owner decided
that double-click opens the property sheet; [UX vocabulary](../UX-PRINCIPLES.md#vocabulary) also assigns it to
inspector naming. Keep double-click, F2 and Enter on a selected card opening Properties with Label focused.
Double-click empty canvas remains quick-add. Do not make either gesture depend on whether children exist.

Use **Open detail**, a magnifier button on a selected/focused system or container, plus a context-menu action
and Properties action from the same action registry. Keyboard users Tab to the button and activate it with
Enter/Space; no new overloaded canvas shortcut. A small persistent glyph indicates existing inner detail;
hover/focus explains “4 containers inside”. The cue is non-colour, but the action is fully reachable by keyboard
and touch. The indicator's count comes from model children, not visible filtered children. An empty parent
offers “Add container inside…” or “Add component inside…” in Properties; it has no false drill-down badge.

When nesting/multiple views exist, turn the **existing diagram title area** into a compact breadcrumb and view
selector, rather than adding another top-bar control:

```text
Commerce  ›  Orders API          [ Components · Request handling ▾ ]
```

Breadcrumb ancestors navigate upward; the selector groups available named views by level/scope, identifies
the current one and offers New view in editing. Context/Container/Component are scopes, not a global mode
that changes every card's type. Show only actual levels; no disabled Code tab. Several inside views open a
small chooser, with the default first and the previous choice remembered for that parent. Flat documents
keep today's title surface. A separate document picker stays available inside the title menu.

Preserve each view's pan/zoom/selection in session state; save `defaultView` and layout, not transient navigation
history. Return to the calling view via breadcrumbs/history with its viewport restored and the parent focused.
Collapsed long breadcrumbs keep the current scope readable. Navigation is not an Undo step or a document edit;
browser Back/Forward can restore navigation using view IDs without changing the document. Esc keeps its current
overlay/selection/live behaviour. Presentation uses the same compact read-only navigation without edit actions.
Invalid/deleted view IDs fall back to the default and explain where the user landed.

| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create a container inside Commerce | Commerce's Properties → Add container inside… opens its inside view and current stencil search. Create one element with `parent: commerce`, one placement clear of overlaps, label focused. One Undo step, including a newly required view.                            |
| Add a component                    | Container's Properties → Add component inside…; description/stencil optional. Documentation-only by default so adding design detail never changes playback. No new replica fields.                                                                                     |

Adding an appearance retains its ID; Duplicate explicitly creates a new element and says so.                                                       |

Auto-layout/Tidy up likewise affect only this view.                                                                                                   |

Reparenting preserves canonical IDs and external relationships, but can change roll-up, scope membership and
shared pool ownership. Source-view placements remain dormant where scope no longer allows them; destination
placements are added clearly. Preview simulation references and pool changes; semantic edits follow existing
run-invalidation behaviour. Undo restores parents, layouts, bindings and format/revision together. Copy/paste
remaps subtree IDs, internal edges, endpoint/pool references and selected view decoration; cross-document
paste previews external references instead of matching labels. Navigation after Undo selects affected things
in a view that can show them, preserving the repository's selection conventions.

### Written UX review

Against the chrome budget: no extra global toolbar, permanent model tree, four-tab level bar, general-purpose
layer panel or second inspector. One conditional title-area selector, compact breadcrumbs and one contextual
Open detail action suffice. Menus remain ≤12 items per level by placing Move/Delete under contextual model
actions; audit actual counts after the refactor. A flat first-time diagram has no C4 settings to complete.
Properties distinguishes “Parent system/container” from “Boundary”; the hint explains ownership once in place.

Check 1280×800, narrow embeds, long labels, both themes, keyboard focus, translated/RTL chrome and reduced
motion. Breadcrumb/selector space must be reserved in fit/export layouts, and badges cannot cover labels or
the selected node's existing quick-add button. RTL mirrors chrome, never the architecture. Every interactive
control gets `data-testid`; implementation text uses `t()` and keys in `src/i18n/en.ts`. This is a written design
review, not a claim of tested UI; every implementation batch still ends with the independent UX gate.

## 4. Simulation across levels

### One execution graph, independent of visible scope

Compile execution from the model, never React Flow's displayed nodes/edges. Choose the deepest **enabled**
execution frontier: atomic containers remain leaves even with documentation components; a structural system
uses its configured descendants; a detail container uses explicitly executable components. Do not choose
an arbitrary globally deepest C4 level and drop shallower external APIs or stores. Each branch can end at a
different depth. Hidden leaves and sources still run, and two views of one API never double its capacity.

V1/V2 can show structure with flat/atomic playback, but disable Live on aggregate views until V3 can render
truthful roll-up. Do not ship placeholders that animate authored Context arrows as if they were execution.
An architecture-only imported model can be navigated without simulation settings; Live explains that no
executable flow exists and points editing users to the relevant Properties.

Converting an atomic container to detailed execution is explicit. Require entry bindings from traffic,
incoming relationships and endpoints to executable components and an explicit exit mapping to outgoing
relationships. Validate all bindings before activation; no “first child” selection or duplicate parent edge.
Traffic profiles, timeline injection/status/props and expectations resolve stable IDs through the same compiler.
Container status applies once to its pool; component status affects that stage only. Parent-level injection
requires a selected entry; ambiguous or unsupported override/metric bindings disable execution with a repair
diagnostic. Documentation annotations and dependencies remain outside executable topology.

C4 components do not get separate fleets. The Container owns replicas, concurrency, CPU/resources, quotas,
readiness and autoscaling. Detailed stages charge their authored work against that shared pool, with an
explicit declared processing/admission contract; a stage cannot multiply parent capacity. Reuse the merged
pool/admission/allocation machinery from planning/P3 and autoscaling rather than invent another ledger.
If that shared-stage contract is unavailable in V3, ship roll-up over atomic containers and keep components
documentation-only with a clear label. Detailed component execution is then a separately reviewed extension,
not independent processors hidden behind C4 notation.

View changes, pan/zoom and layout edits must not change engine topology ordering, PRNG consumption, clock,
particle IDs, routing, physical delay, queue state or checkpoint compatibility. Renderer paths use view
geometry; existing animation travel defaults remain compiled from canonical configuration, never aggregate
edge length. A semantic change invalidates/restarts as today; a layout change only refreshes the renderer.

### Traffic, health and capacity: define every denominator

Projected arrows carry **cross-boundary delivery attempts**. At each canonical forward-send event, add its
represented real-message count once to the current projection's contributor group. Use a shared simulated
measurement window for rates: summed count deltas divided by that window, not a sum of unrelated smoothed
node throughput values. Failed arrivals remain attempts; admitted/completed work is a separate metric.
Dependencies produce no traffic. Replies, retries and DLQ trips retain separate categories and provenance.

Fan-out copies and repeated crossings are real attempts, not unique business transactions. An internal path
collapsed into one system contributes no external traffic. Do not sum every hop and label it “orders/s”.
For unique-family counts, use `rootId` only when bounded lineage supports the complete interval; otherwise
mark unavailable rather than infer unique demand from attempts. Aggregate animations sample canonical
crossings under the existing drawing budget; counter values never come from visible dots.

| Aggregate readout      | Definition and limitation                                                                                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Incoming/outgoing rate | Boundary-crossing ordinary attempt counts in real units/window. Separate Requests/Messages and retry/DLQ categories; exclude visual replies from request demand.                                                                                                                      |
| Waiting work           | Sum disjoint queue/processor backlog storage locations once. Broker group lag is delivery obligations, retained log size is storage, and in-flight work is another category; show those separately, never add them as unique messages.                                                |
| Failures/losses        | Summarize disjoint canonical outcome events, with retries/failed attempts apart from terminal drops/dead letters/blocks (and P3 rejects when supported). Cross-link the owning leaf.                                                                                                  |
| Health                 | “2 affected of 8 executable elements”, naming the worst observed cause; documentation-only elements are “Not simulated”. No numeric availability/SLA or green overall state when required detail is unknown.                                                                          |
| Replicas/resources     | Sum each physical pool once. Components share the Container count. Show ready/starting/draining and CPU/memory only when implemented, with their original units/denominators.                                                                                                         |
| Capacity               | Per entry/workload configured feasible rate or bottleneck and limiting leaf from the shared planner. Never sum serial stage capacity or average percentages; independent workloads require separate lines and shared-budget accounting. Unknown/nonconvergent inputs suppress sizing. |

Constructed acceptance example: 100 requests/s enter Commerce, traverse three internal components and call
Payments once each. Context shows 100 incoming and 100 outgoing requests/s, not 300 or 400 “processed/s”.
If each request fans out to two external deliveries, it shows 200 outgoing delivery attempts/s, still 100
input requests/s. Ten retried calls appear in the retry count without inflating the ordinary input count.

At Container level show the application's external demand, observed waiting/health and limiting stage.
A serial 100/s stage followed by 40/s stage gives at most 40/s for that workload, not 140/s. At Context level
prefer “Commerce is waiting on Payments; Charge handler limits this path” and Open detail over editable
system replicas. Capacity fixes target the actual leaf/pool, are undoable, and explain scope before applying.
Nominal planning and observed simulation are labelled separately. Keep caller waits, end-to-end success and
meaningful request p95 behind their existing approval/implementation gate; C4 does not supply those semantics.

### What Live means on Context

Live on Context answers **who is interacting, where work is accumulating and which modeled dependency/path
is troubled**. It is the same local simulation clock and scenario, with a few cross-system particles and
compact summaries. Opening Commerce keeps the same run/time and reveals the contributing containers; opening
Orders API reveals modeled component detail or states that execution is atomic. Nothing calls real systems
or pulls production telemetry. A system with only authored documentation relationships stays static and
explicitly unmeasured. Narration/trace focus on a hidden component highlights its visible ancestor, with
Open detail available; it never forces a view switch in the middle of a presentation.

Maintain indexed count deltas on engine events and build only the active projection. Do not scan trace history
or all retained messages per frame. Parent maps, contributor sets and pool ownership compile once per semantic
generation. Bound metric windows and recent projection caches. Checkpoints restore the canonical counters,
compiler generation and simulation state; reconstruct projection from them so switching views and scrubbing
cannot lose activity or double-charge it. Respect existing sampling, particle, source-volume and planner limits.

## 5. Other features and interop

### Checks and planning explanations at each level

Run current structural/capacity rules over the canonical executable graph, then project findings by target ID.
A filtered view cannot make a missing reader disappear or turn a hidden gateway into a bypass. Existing
`checks.off` and human-authored `(rule,target)` ignores remain model-scoped. An ancestor badge counts distinct
findings, not occurrences across layouts; opening it lists leaf evidence and navigates to an appropriate view.
Architecture-only details can get naming/ownership/reference diagnostics, but no fabricated capacity result.

Context explanations state responsibility, connected systems and modeled overall trouble. Container explains
calls/consumption, one shared pool, backlog and limiting routes. Component explains its responsibility and its
share of the container budget. New hierarchy/view-reference validation is an ingress error with a repair hint;
advisory architecture checks still do not block saving or Live. Missing capacity/entry configuration disables
only the unsupported analysis/execution, never silently substitutes another target. No duplicate rule engine.

### Routing, endpoints and autoscaling

Keep [routing.md](routing.md)'s Request route, gateway rule and node-owned endpoint identities distinct from
C4 views and components. A `POST /orders` endpoint is not automatically a component. Container execution owns
its endpoint records; an explicit handler binding can name a component. A higher-level arrow lists endpoint
and route contributors on inspection but cannot edit a mixed route table as one rule. Roll-up retains message
filters, subscriptions, DLQ roles, shared quotas and original edge IDs; it never reroutes through a summary.

Autoscaling acts on a runtime pool/application, not a view, Person or Software system. Show the Container's
one desired/ready fleet and limiting input assignment; each component must not acquire its own HPA. System
summaries list affected containers and policy limits without summing percentages or presenting a single
system-wide max replica control. An existing shared vendor quota stays shared across all appearances.
Preserve [autoscaling.md](autoscaling.md)'s missing-metric, readiness, partition, controller-version and
approximation rules; structure provides no measurements or cluster scheduler.

### Imports: no inferred component architecture

Keep existing Terraform/Kubernetes/Compose/AsyncAPI imports flat by default. Offer an opt-in multi-level
preview with an authored system name and explicit ownership selection. Kubernetes workload → candidate
application Container; Service/Ingress → routing/infrastructure according to the existing importer; namespace,
cluster, pod and Docker container → deployment facts, **not** automatic C4 systems/components. Multiple
manifest containers may be sidecars or separate applications; flag uncertainty rather than turn them into
independent component fleets. Retain HPA/KEDA targets on the existing exact workload identity.

Terraform managed database, queue/topic, function or application → candidate data/application Container.
Module/resource nesting and resource-group/VPC membership describe provisioning/deployment, not software
ownership or internal components. Never guess Component structure from Terraform or Kubernetes. Require
authored source/module evidence or a reviewed explicit mapping for it. Import preview states inferred vs
authored ownership and what is unclassified. Reimport preserves IDs using existing importer identities,
previews moves/deletes/ambiguous matches, retains measurements/layouts, and applies one Undo step.

Parsers stay local, bounded and lazy; reject oversized/deep/cyclic inputs, sanitize text and report unsupported
constructs. No secret values, credentials, remote discovery, executable manifests or vendor API requests.
This design adds no outside endpoint or CSP connect-src exception.

### Exports and restricted text import


Structurizr export cannot rely on its first-implied-edge strategy for complete provenance. Emit our intended
summary relationships explicitly with implied relationships disabled where necessary; retain original
relationships and namespaced safe metadata if the target supports it. Text interchange does not implement
arbitrary executable DSL directives. [Structurizr language](https://docs.structurizr.com/dsl/language),
[Implied relationships](https://docs.structurizr.com/dsl/cookbook/implied-relationships/).

V4 import first supports **a bounded declarative Structurizr subset**: model elements, parent nesting,
relationships, supported scopes and simple include/exclude. Reject remote/local includes, workspace extension,
scripts/plugins, code discovery and theme fetches, with precise diagnostics; never execute them. A browser
parser is its own data interpreter, not a JVM/plugin runner. Proposed input cap 5 MiB, same model/view/placement
budgets as native, bounded tokens/text and explicit supported grammar. Reject unsupported statements atomically
or let the person explicitly accept a reported partial import; never silently drop directives that alter scope.

Mermaid C4 import accepts the emitted static subset plus known C4 boundary/relationship statements into one
view; aliases map to IDs within that file. Importing separate snippets does not merge objects by matching
aliases/names unless a trusted exported manifest maps them. Report unsupported Dynamic/Deployment syntax and
styling. Imported relationships are documentation-only until explicitly configured; no guessed rates,
latency, health or replicas. Reuse existing flowchart import rather than change its interpretation globally.
Round-trip fixtures must distinguish semantic fidelity from exact geometry and playback.

### Embeds and Interactive HTML

Include the supported v3 reader, projection and compact view navigation in the self-contained read-only
viewer. Default view comes from export choice or `defaultView`; deep links carry a validated view ID. Open
detail, breadcrumbs and switching work offline while one run continues. No edit controls, inspector renaming,
remote icons/parser fetches or new backend. Support the same runtime revision before allowing a file export
with enabled detailed execution. The app's CSP and the existing viewer's export security rules still apply.

**A selected view is not access control.** An all-view HTML/embed/native export contains inner detail, including
currently hidden records. Say so in Share/Options. A “Current view only” export must construct a minimal
standalone drawing with no hidden descendants, relationships, simulations, notes or embedded original payload;
it loses drill-down/full playback and reports that. A scoped subset with full playback requires closure over
all executable dependencies and can disclose them; never market that as hiding internals. Privacy/password
gates cover the entire emitted file, not per-view permissions. Keep the existing Private rules and access wording.

HTML/embed switching must fit narrow hosts, respect wheel-scroll conventions, reduced motion and keyboard
focus. Test password and no-network exports with two levels, and ensure a requested restricted export contains
no descendant marker even in serialized payload. The released skill viewer and site viewer must support the
same native format before multi-level files are offered for export.

### Agents: WebMCP and the skill

Extend existing tools rather than add one tool per level. Proposed `describe_diagram` options include `viewId`,
`scopeId` and bounded depth; return canonical IDs/parents, available views, hidden counts, projected relationship
contributors and evidence labels. Default description still works for flat diagrams. `check_diagram` remains
canonical with optional scoped presentation; agents cannot write check ignores/off.

Extend `edit_diagram` with `add_element` (C4 kind/parent/stencil), `reparent`, `add_view`, `update_view` and
`place_in_view`, plus canonical `connect` and existing updates. These are proposed operations, not current
APIs. `add_node` remains the flat compatibility operation. Its existing `in` means Boundary and **must never
be reinterpreted as semantic parent**; new `parent` and `viewId` are explicit. `set_meta` can select defaultView.
Resolve batch keys to IDs, validate the complete final graph and return the same preview/diagnostics as human
editing. Every batch is atomic, dry-run capable and one Undo step; no incidental navigation/pan/inspector opening.

Simulation tools target canonical executable IDs and explicit entry bindings, not aggregate display arrows.
They can observe rolled-up metrics with their categories/units but never infer unmodeled totals. Update the
skill's schema, validator, layout instructions and synthetic examples to teach model identity, parent vs Boundary,
per-view placement and privacy/export scope. Future implementation runs `pnpm schemas`; check viewer freshness
and run `pnpm skill:release` when stale, setting the marketplace version exactly one patch above then-current

## 7. Decisions rejected, deferred and open

- **Separate diagrams per level or copied model objects:** rejected; names, relationships and simulation
  diverge. Stable canonical IDs and view geometry solve the maintenance problem.
- **Double-click drill-down or zoom-triggered automatic level changes:** rejected; conflicts with the owner's
  Properties gesture and makes navigation surprising. Explicit Open detail is predictable.
- **Boundary = semantic parent, Kubernetes container = C4 component:** rejected; visual/deployment membership
  differs from application ownership. Imports cannot prove internal code structure.
- **One simulation per view, processors for aggregate cards, independent component replicas:** rejected;
  invents traffic/capacity and changes the run when navigating. One execution frontier and owned pools are required.
- **Sum all hop counters/throughput/capacity or average health percentages:** rejected; double-counts internal
  work, fan-out and serial limits. Rates/outcomes have explicit units, scope and provenance.
- **View hiding as privacy, unrestricted DSL execution, remote model discovery:** rejected; hidden records can
  remain in the payload and executable imports break the browser-only data contract. Pruned export is separate.
- **Code graph editing, alternate semantic hierarchies, environment-specific deployment instances and automatic
  source-code extraction:** deferred; each adds another contract beyond the first useful three levels.
- **Open before V1:** settle exact v3 budgets/schema URLs against native import limits, supported realization
  metadata and fallback layout rules. V3 must settle the merged pool/entry/exit contract and measurement window;
  V4 must publish the supported text grammar and loss report. These are explicit implementation decisions,
  not grounds to fabricate execution semantics in the research.

This document introduces no user-visible application change and adds no release-note promise. Implementation
PRs must add [RELEASE-NOTES.md](../RELEASE-NOTES.md) entries for what they actually deliver.
