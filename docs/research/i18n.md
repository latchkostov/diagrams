# Internationalization: research and plan (2026-10-13)

The owner's request: "Switch your language from English to whatever else, and for everything in the app to reflect
that. Some things are going to be pretty generic. But other languages have their own internationalization: it should
match what people actually use, not translate verbatim if that's not what they use. For things like Kafka topics, I'm
not sure how they're usually presented. Research the best ways. Pick the top languages, or, if the translation is
modular enough to inject easily, cover all the typical languages an operating system covers, even Bulgarian and smaller
languages that have good internationalization across applications."

How to use it day to day (adding strings, adding a language, the glossary, corrections): [`docs/I18N.md`](../I18N.md).

## Summary

- **Languages: the typical operating-system set, 37 plus English at launch.** That's every Windows base language
  (fully localized Windows), plus Indonesian, Vietnamese and Hindi, which Apple, Android and Chrome all ship. The
  architecture makes a language one JSON catalog and one glossary file, loaded only by the people who use it, so the
  marginal cost is translation quality, not code or bytes. Tier 2 (Persian and Urdu, which complete right-to-left
  coverage; Catalan, Malay, Bengali, Tamil, Telugu, Marathi, Kazakh, Filipino; es-419 and fr-CA) and tier 3 (the rest
  of Android's and Windows' language packs) follow on demand.
- **Terminology: a glossary per language, following developers, not literal translation.** Vendors (Microsoft, AWS,
  Google) mostly translate messaging terms, often by machine and sometimes wrongly; developers and the specialist
  vendors (Confluent, Red Hat, Yandex, Alibaba) keep many in English or transliterate them. German developers say "das
  Topic" and "die Consumer Group"; Japanese write トピック and コンシューマーグループ; Bulgarian developers write the
  English "topic" (no source uses "топик"), and "тема" clashes with the app's light/dark _theme_. The glossary records
  the choice per term per language, with "keep in English" where that's what people use, and the validator enforces it.
- **Library: none. A custom compile-time ICU-lite.** No i18n library fits the entry budget (Lingui, the smallest
  full one, is about 3.2 kB gzip with its React bindings; i18next and FormatJS are 14 to 20 kB). The build inlines each
  message's English where it's used and compiles ICU plurals to plain functions; the runtime is a lookup and a store,
  about 0.3 kB gzip (0.86 kB with starting in a language, the switch and right-to-left menus); each language is a lazy
  chunk.
- **Honesty:** every non-English language says it's machine-translated and links to a prefilled GitHub issue to
  suggest a better translation. No accounts, no server.

### Keeping quality across many languages

A broad set is only worth it if each language reads right. The plan:

1. **One glossary per language**, decided once from research (below), enforced by the validator on every message: a term
   rendered against it (or left out) fails `pnpm i18n check` and the unit test.
2. **Machine translation with the glossary, then automated checks** (§7): placeholders, ICU syntax, plural forms the
   language needs, protected names, leftover English, length.
3. **Honest about it**: non-English languages say "Translated by machine" in the Language dialog, with a one-click
   correction link. A language a fluent person has reviewed drops the notice (`reviewed: true` in its meta file).
4. **The pseudo-locale** (en-XA) in the dev server and the e2e build shows untranslated and overflowing UI at a glance.
5. **Tier 1 reviewed first** where the owner has reviewers (Bulgarian, German), then by request.

## 2. Technical terminology

### What vendors and developers actually use

- **Vendors translate; developers don't.** Microsoft, AWS and Google translate "topic" as the local word for "theme"
  (Thema, rubrique/sujet, tema, argomento, onderwerp, temat, konu, тема, 주제). Confluent keeps it ("Topics", "les
  topics", "los topics", 토픽), as do Yandex Cloud (топик), Alibaba Cloud ("Topic", "Group") and the developer
  communities (Habr, dou.ua, dev.bg, Korean blogs). Only Brazilian Portuguese "tópico" is universal.
- **Much vendor localization is machine-made, and wrong in places.** Microsoft Learn marks it (`ms.translationtype:
MT`); Google Cloud's localized pages carry `lang="xx-x-mtfrom-en"`. Mistakes found: zh-TW 無效字母佇列 ("invalid
  letter-of-the-alphabet queue") for dead-letter queue (Microsoft and AWS), Italian "code di lettere non scritte"
  (AWS), Korean "배달 못한 편지 대기열" (AWS), Turkish "Yapımcı" (a film producer) for producer (Microsoft), Dutch
  "Afstand" (distance) for offset (Microsoft), Arabic three different words for queue on one page. For bg, uk, sk, sl,
  hr, sr, ro, el, da, nb, fi, et, lv, lt, he, hi, th and vi, Microsoft Learn shows the Service Bus docs in English.
- **Same-word clashes inside this app.** In Bulgarian, Ukrainian and Greek, "topic" and "theme" are one word (тема,
  тема, θέμα), and the app has a light/dark theme. In Bulgarian, "consumer" and "user" are both потребител (also
  Croatian korisnik, Lithuanian vartotojas). Russian раздел (Microsoft's partition) also means a UI section.
- **Japanese long vowels:** Microsoft's style guide (after the 1991 Cabinet notice) adds ー to words ending in -er, -or,
  -ar: コンシューマー, プロデューサー, ブローカー, サーバー; longer words with other endings don't: メモリ, レイテンシ.
  Google follows it; Red Hat adds ー everywhere; AWS is inconsistent. **Follow Microsoft**, and write compounds joined
  (コンシューマーグループ, デッドレターキュー, as AWS, Red Hat and Confluent do), with a half-width space beside Latin
  words and numbers (API ゲートウェイ).
- **German genders** for kept English words (Duden where listed): der Broker, der Cache, das Gateway, das Backlog, das
  Event, der Consumer, der Producer, der Offset, der Load Balancer; by analogy das Topic (das Thema), die Queue (die
  Warteschlange), die Consumer Group.
- **Russian:** топик (Yandex, Habr), not Microsoft's тема; партиция, not раздел.

### Bulgarian, as the owner asked

- **"топик" or "topic"?** No Bulgarian source writes "топик": every search hit was Russian. Bulgarian developers write
  the English word, inflected in Latin ("Topic-а", dev.bg) or "теми (topics)". **Use "topic", kept in English**; never
  "тема" (it's the app's theme).
- **"опашка" for queue: yes.** Standard everywhere (Microsoft terminology, SoftUni's "стекове и опашки", Nakov's
  textbook, dev.bg).
- **"консуматор" or "consumer"?** No Bulgarian source uses "консуматор"; Microsoft and dev.bg write "потребител", which
  is also "user". **Keep "consumer"** in Latin in technical labels (as dev.bg writes "producer-и"), "консуматор" only
  where Cyrillic is needed in running text.
- **Microsoft's Bulgarian Service Bus terms:** none in its docs (they're English); its terminology collection gives
  тема (topic), опашка (queue), абонамент (subscription), "опашка на недоставените съобщения" (dead-letter queue).
- Register: formal **Вие**; quotes „…“; a space groups thousands, a comma marks decimals.

### The glossary approach

`src/i18n/glossary/terms.json` lists the terms every language decides (36 today: the messaging and infrastructure
terms, and the app's own vocabulary from `docs/UX-PRINCIPLES.md`), with how to find each in English and what it means,
and the names never translated (`doNotTranslate`: Live Diagrams, Kafka, Azure Service Bus, AWS, Google Drive, draw.io,
Mermaid, JSON…). Each language's `src/i18n/glossary/<code>.json` gives, per term:

```json
"topic": { "use": "Topic", "keepEnglish": true, "match": ["Topic"], "avoid": ["Thema"], "note": "das Topic, die Topics" }
```

- `use`: the form translators write; `match`: stems the validator accepts (inflected forms: диаграм matches диаграмата);
  `avoid`: forms that must not appear (тема in Bulgarian); `keepEnglish`: developers keep the English word; `except`:
  keys where a natural translation leaves the term out.
- `pnpm i18n check` and `src/i18n/catalogs.test.ts` fail when a message whose English has a term renders it against its
  language's glossary, or changes a protected name.

## 3. What gets translated, and what never does

**Translated:** the UI chrome (menus, dialogs, buttons, tooltips, accessible names, toasts, errors and their fixes);
the stencil _category_ names and descriptions; the simulation's explanations (the live callout, hover cards, the
trace card, checks' "Why"); the start card and the shortcuts sheet; and the static pages, in a later batch:
`public/privacy.html` and `terms.html` as one page per language (legal text, so reviewed, never only machine-made; until
then English with a note), the sign-in pages (short; translate), the `/skill/` page (English: its readers are
developers installing an agent skill).

**Never translated, and why:**

- **The person's diagram:** labels, subtitles, notes, titles, boundary names. It's their content, and they share it
  with people who may read another language.
- **Product and stencil brand names** (Kafka, Azure Service Bus, AWS, Cisco, PostgreSQL): that's how they're searched
  for and printed in every language. The _category_ ("Messaging", "Databases") is translated.
- **File formats and JSON keys** (`.diagram.json`, `nodes`, `edges`, `props`): files move between people with
  different languages and must open the same everywhere.
- **WebMCP tool names, their schemas and the agent-facing descriptions**, `llms.txt`, the skill: agents are prompted in
  English and match tool names exactly; a translated description changes how a model picks tools, and a
  person's language says nothing about their agent's. Results an agent relays to a person (a check's message) can be
  localized later, as a separate field.
- **On-device model prompts** (Chrome's Prompt API): the prompts are tuned and evaluated in English (docs/research/
  on-device-model.md); the person's request can be in any language and the model answers with diagram JSON.
- **Simulation numbers' units in code** (msg/s in files and URLs). Displayed rates are formatted for the language.

## 4. Formatting

All through the browser's `Intl`, so no locale data ships:

- **Numbers** `Intl.NumberFormat`: 1,234.5 (en), 1.234,5 (de), 1 234,5 (fr, bg, ru), 12,34,567 (hi). `ar` writes
  Western digits by default (Microsoft's Arabic style guide asks for them); `ar-SA` would use Arabic-Indic digits, so
  the catalog is `ar`. Persian (tier 2) uses Persian digits, as people there expect.
- **Rates** ("1,200 msg/s"): a number formatted for the language and a translated unit message (`format.rate`); most
  languages keep "msg/s". **Percentages** `style: "percent"` (42 % in de and fr). **Durations** `style: "unit"`
  (850 ms, 1,2 s). **Dates** `toLocaleDateString` (Thai uses the Buddhist calendar by default, as Thai users expect).
  **Relative time** `Intl.RelativeTimeFormat` with `numeric: "auto"` ("vor 5 Min.", "gestern", "昨日"); English keeps
  the app's own "5 min ago". **Lists** `Intl.ListFormat` ("A, B und C"; "A、B、C").
- **Plurals** with ICU `plural` and `Intl.PluralRules`: the validator requires every form a language uses for whole
  numbers from 0 to 1000. English and German need one/other; French one/other (its "many" is only for millions);
  Bulgarian one/other; Russian, Ukrainian and Polish one/few/many/other; Czech and Slovak one/few/other (+ many for
  decimals, not whole counts); Lithuanian one/few/many/other; Latvian zero/one/other; Arabic zero/one/two/few/many/other;
  Hebrew one/two/other; Japanese, Chinese, Korean, Thai, Vietnamese and Indonesian other only.
- **Gender:** not needed so far. The UI never refers to the person by gender; Hebrew uses the neutral plural and
  Arabic the generic imperative. ICU `select` is there if a message ever needs it.

## 5. Layout

- **Text expansion.** German and Finnish run 30 to 40% longer than English (Greek, Russian and Hungarian about as
  much), CJK about half. Budget: every converted surface fits **English + 40%** at 1280 × 800, checked with the
  pseudo-locale (every message 40% longer, in brackets, so a cut shows). Where it can't fit: menus and dialogs wrap (no
  fixed widths on text), the top bar's labels already hide below 1100 px (`label-optional`), buttons wrap their words
  (the checks card's rule, round 28). The validator warns when a translation is more than 1.6× English.
- **Right to left** (ar, he; fa and ur in tier 2). `<html dir="rtl">` mirrors the chrome: the top bar, menus (they open
  from the trigger's other edge and submenus to the left; the arrow keys swap), dialogs, the start card. The converted
  areas use logical properties (`margin-inline-start`, `padding-inline`, `inset-inline-end`, `text-align: start`), and
  their chevrons flip. **The diagram doesn't mirror**: `.react-flow` keeps `direction: ltr`, so a diagram reads the
  same everywhere (A → B stays left to right; that's its data, not its text), as Figma, Miro and draw.io do. Arabic or
  Hebrew labels inside nodes still render right to left by the bidi algorithm. Mixed text: Latin names inside RTL
  sentences (Kafka, Google Drive) are kept inline, as Microsoft and Google do; the bidi algorithm orders them.
  Later batches convert the side panels (stencils, inspector, AI panel) to logical properties.
- **CJK and complex scripts.** The UI font (Mona Sans) covers Latin and Vietnamese only; every other script falls back
  to the system UI font (`system-ui`, Segoe UI, Yu Gothic UI, Microsoft YaHei UI, Malgun Gothic, Leelawadee UI, Nirmala
  UI; PingFang, Hiragino; Noto on Android and Linux). Under the strict CSP (`font-src 'self' data:`) that's what we
  want: installed fonts aren't fetched, so the policy allows them, and shipping CJK fonts (several MB each) would be
  wrong anyway. `<html lang>` makes the browser choose the right Han glyphs (Japanese vs Simplified vs Traditional
  shapes). Line breaking: browsers break Thai with a dictionary and CJK between characters; Japanese and Chinese get
  `line-break: strict` (no small kana or closing punctuation at a line's start), Korean `word-break: keep-all` (it
  breaks at spaces), and compound-heavy languages (de, nl, fi, sv, da, nb, hu, el) `hyphens: auto` in menus and
  dialogs, so a long compound wraps instead of overflowing.

The constraint decides it: the entry had about 20 kB of room under its budget, and the whole foundation was to cost
about 0.3 kB. No library fits; Lingui (the best of them, and the same architecture) is ten times that. So:

- **Source** calls `t("file.new")`, `t("file.libraryCount", { count })`, `tRich("share.linkDesc", { b: … })`.
  TypeScript checks the key against `src/i18n/en.ts` and the arguments against the message itself (a type-level
  reading of its placeholders: `{count, plural, …}` needs a number).
- **The build** (`scripts/i18n-plugin.ts`) inlines the English at each call site: plain text as a tagged template,
  t`New diagram`, whose text is also the lookup key (about half a byte a string, gzipped); a message with
  placeholders as `t(41, v=>…, {count})`, its English compiled to a small function with English's plural rule built in.
  So English lives in the chunk that uses it, and no English catalog is loaded anywhere.
- **Each other language** compiles to a lazy chunk keyed the same way, with its plurals calling `Intl.PluralRules`
  through a few helpers that come with the catalog.
- **The runtime** (`src/i18n/index.ts`) is a lookup, a store for `useSyncExternalStore` and the start-up check; what
  switches languages (`src/i18n/load.ts`) loads only for someone who isn't in English, or opens the Language dialog.

Measured (gzip −9, entry chunk, against the same commit without it): see `docs/I18N.md` § Size and round 33.

## 7. Producing translations, and keeping them right

- **Catalogs:** `src/i18n/locales/<code>.json` (key → ICU message) and `<code>.meta.json` (reviewed or not; a hash of
  each message's English at translation time).
- **Producing:** `pnpm i18n todo <code>` prints what a language needs (missing and stale messages), its plural forms,
  its glossary and the rules, as JSON for an AI (or a person) to fill in. The launch translations were made that way:
  an AI translator per language group, given the glossary research above and the app's vocabulary, then validated.
- **Checks** (`pnpm i18n check`, and `src/i18n/catalogs.test.ts` in CI): ICU syntax, placeholders and tags identical
  to English's, every plural form the language needs and none it can't use, protected names unchanged, the glossary
  followed; warnings for leftover English, length over 1.6× English and French spacing.
- **Honest in the UI:** the Language dialog says "Translated by machine. Something reads wrong? Suggest a better
  translation on GitHub." The link opens a prefilled issue (language, where, what it says, what it should say). A
  correction becomes a pull request to the catalog; a language that a fluent person has reviewed is marked
  `reviewed: true` and the notice goes.
- **When English changes:** a new key shows in English everywhere until translated (the runtime's fallback); a changed
  English message is **stale** (its hash differs) and `pnpm i18n check` lists it, while the old translation keeps
  showing. CI reports both; neither fails a build, so English work never waits on 37 languages.

## 8. Choosing the language

- **Default:** the browser's (`navigator.languages`, in order), resolved the way operating systems fall back: the same
  language and region (pt-BR), the same language and script (de-AT reads de; zh-HK reads zh-TW, Traditional), the same
  language in another script (sr-Cyrl reads sr-Latn); Portuguese outside Brazil reads pt-PT; `no` and `nn` read `nb`;
  else the next preference; else English (`pt-BR → pt → en`).
- **The switch:** View ▸ **Language…** and Ctrl+K **Language…**, a dialog listing every language by its own name, with
  "Browser default" first and a search field. The row also says "Language" in English when the UI isn't English, and
  the palette always matches "language", so someone who can't read the language they landed in finds the way back.
- **Kept** in `localStorage` (`diagrams.locale`) through the app's storage helpers; **Clear everything** removes it with
  every other `diagrams.*` key, so the app comes back in the browser's language.
- **`<html lang dir>`** follow the language: screen readers pronounce it right, the browser picks fonts and hyphenation,
  and `dir="rtl"` mirrors the chrome.
- **Self-hosting:** `VITE_LOCALES` (docs/SELF-HOSTING.md) limits the languages a copy offers ("de,en": German or
  English by browser, German otherwise), or forces one ("de": German for everyone, no Language choice). Catalogs it
  doesn't offer aren't built.
