## Self-host S3: relay rooms

Reviewed the S3 room consent, connection failures, privacy gates and Share chooser against the UX
principles and approved server proposal. This is a source review; browser behavior is covered by the
implementation's targeted verification, not claimed as visual inspection here.

## Chrome and consent

No global controls or settings are added. Edit together remains in Share and the existing action entry
points; server configuration stays a deployment concern. The existing dialogs retain one primary
action and their keyboard/focus behavior.

Server start and join disclosures name the relay host, explain the IP-address and room-presence
exposure, and retain the encryption statement. They omit the public peer-IP disclosure. Services names
the same host. Public-room disclosures retain their existing wording.

## Failures and privacy

Server-unreachable and room-full messages describe the cause and give a next step. Retry remains
available; an existing room still offers Save a file copy. Public builds with no trackers retain the
specific no-servers explanation rather than a generic connection failure.

Private diagrams cannot start rooms in either transport mode. The blocked Edit together dialog has a
single Done action and no privacy escape. Server-mode Share also omits Make it not private, including
builds that enable share links. The existing generic Share privacy action remains in public builds;
this change does not broaden the room dialog into a way to remove privacy.

## Review outcome

No additional chrome or layout changes are needed. The initial question about the public Share privacy
action was resolved as preservation of existing general sharing behavior; collaboration's blocked
surface continues to offer no escape. No remaining UX findings in the reviewed S3 surfaces.
