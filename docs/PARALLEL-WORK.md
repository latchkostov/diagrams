# Parallel work without shared logs

Each PR writes a new `YYYY-MM-DD-short-slug.md` file in `docs/release-notes/` and, for its UX review,
`docs/design-review/`. Keep the existing `## Heading` section format; the heading may include the date,
PR number and review round. Slugs must be lowercase words separated by hyphens. Pick a descriptive slug
so parallel branches create different paths. `pnpm test` validates names, dates, nonempty text and headings.
Screenshots can still live in subdirectories of `docs/design-review/`; they are not fragments.

`pnpm notes` prints all release fragments newest first, then frozen history. `pnpm notes design` does the
same for reviews; `pnpm notes backlog` prints current follow-ups. Same-day entries sort by filename descending.
Redirect stdout if needed (`pnpm --silent notes > notes.md`); never commit a compiled view. The old
RELEASE-NOTES.md and DESIGN-REVIEW.md URLs are small landing pages linking the directories and frozen histories.
Historical anchor links point to the history documents. Offline packages embed the complete release notes,
using the same compiler, rather than copying the landing page.

Independent follow-ups live in `docs/backlog/`, one dated file per finding or related batch. Edit or remove
the affected entry when it lands; don't prepend to BACKLOG.md. Existing items moved intact, including their
resolution status and measurements. Undated entries use their migration date. UX-PRINCIPLES.md remains the
shared contract: its last 30 days of edits refine vocabulary, gestures, default behavior and chrome, rather
than append PR decisions. New reviews belong in fragments; change a principle only when the contract changes.

## Regeneration

`pnpm regen` runs schemas, the skill viewer refresh and i18n validation. Runtime translation catalogs are
generated by Vite from authored English/translations; there is no separate committed i18n output. Regen
never translates or stamps messages, and never updates parity goldens. Run `pnpm parity` separately;
use `pnpm parity:update` only for intended output changes and review every changed golden.

| Artifact                                                                                                       | Policy and reason                                                                                                                                                 |
| -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `public/schema/*.json`                                                                                         | Untracked build/dev output. Vite serves/emits them directly, including standalone Vite builds; contracts are tested in memory.                                    |
| Skill `scripts/lib/{app.mjs,inject.mjs,spec.json,viewer-template.html,icons.json}` and `reference/stencils.md` | Committed: marketplace installs run directly from git, without the app's dependencies or a build.                                                                 |
| Skill `reference/{format,simulation}.md`                                                                       | Authored prose with generated regions. Committed for git installs; sync merges prose before regenerating regions.                                                 |
| `vercel.json`                                                                                                  | Committed: Vercel reads deployment configuration before the build.                                                                                                |
| Generated `deploy/self-host/` server configs/policies                                                          | Committed: people copy these directly and images consume them; no local build should be required. README files and Helm/Kubernetes source templates are authored. |
| `dist/`, skill zip, standalone page scripts, generated example metadata and locale catalogs                    | Already untracked build output; remain so.                                                                                                                        |
| Locale catalogs, glossaries and translation source hashes                                                      | Authored/reviewed translation inputs, even when initially machine-translated. Never mechanically overwrite them during sync.                                      |
| Parity goldens, benchmark baselines, lockfile                                                                  | Deliberate review artifacts or dependency state; never treat them as disposable generated conflicts.                                                              |

`scripts/generated-files.json` is the explicit allowlist used by sync. Committed generated files (including
partially generated references) carry `linguist-generated` attributes. There are no merge drivers or hooks
to install. When introducing another generated output, update the generator, allowlist and attributes together.
Staleness checks direct contributors to `pnpm regen`; `pnpm skill:check` remains informational.

## Plugin updates

The marketplace omits `version`, and the skill has no versioned plugin manifest. Claude Code's documented
[commit tracking](https://code.claude.com/docs/en/plugins/host-marketplace#release-a-new-version) then uses
commits to distinguish updates. `pnpm skill:release` refreshes assets only: no patch arithmetic, no manifest
edit, no bot and no post-merge commit. The former master-plus-one rule is retired. Existing users can run
`/plugin marketplace update livediagrams` or `claude plugin update livediagrams@livediagrams`; background
updates require enabling auto-update for this marketplace. A marketplace pinned to a branch/tag still follows
that ref. Unrelated repository commits can also cause an update; this is acceptable for this single-plugin repo.

On 2026-10-17, the branch-protection endpoint reported master unprotected, and the rulesets endpoint returned
no rulesets. We still keep signed contributor commits. Commit tracking avoids requiring a bot signing key,
repository write permissions, release races or any action that pushes to master.

## Sync

Start with a clean, committed branch, then run `pnpm sync`. It fetches origin and rebases onto origin/master,
signing replayed commits. At a conflict it:

1. Takes rebase stage 2 (the rebased upstream) for fully generated files, then runs `pnpm regen` before
   continuing. Regeneration runs again at the end, even if Git merged generated text without a conflict.
2. Merges skill reference prose with generated regions neutralized, then regenerates those regions.
3. Three-way merges English string keys. Separate additions and identical edits merge; competing edits,
   deletion versus edit, unknown syntax and duplicate keys stop for review. It parses data without executing it.
4. Lists remaining real conflicts and stops. Resolve and `git add` each file, then `pnpm sync --continue`.
   Use `git rebase --abort` while the rebase is in progress to return to the starting point.

Only allowlisted generated files are staged automatically. If final regeneration changes files after the rebase,
sync amends the final commit with a signature; review the rewritten branch before pushing. A signing or generator
failure stops the command. Failed regeneration after a completed rebase leaves its edits available for review;
rerun regen, commit the outputs and validate. There is no implicit stash or push.

Parity goldens always stop for review, including textual conflicts. Sync never invokes parity updates or
stages goldens. After any rebase run i18n/skill checks, tests and parity; a clean merge is not proof of output parity.

Splitting English now would touch 37 translation/stamp workflows, type inference, catalog ordering and the
build compiler for little benefit beyond the key union. A future split can use area modules with a generated,
typed aggregator, retaining sorted lookup IDs and current exports; prove identical catalogs, bundle startup
chunks and parity before adopting it. Translations remain flat unless their workflow is redesigned separately.

The best code splits for a separate task are CanvasView's interaction controllers (keyboard, pointer/selection,
menus and overlays), canvas.css by those same surfaces, Lab presets into domain modules with an index, and
useEditor's document/history versus selection/gesture commands. Preserve lazy boundaries and public APIs.
Those shared implementation contracts and their tests are untouched here.
